# TrustedHands frontend

This pnpm workspace holds the TrustedHands web apps. The API lives in the separate `backend` repo.

```
apps/
  client/     Client PWA (Next.js 16), port 3001
  admin/      Admin console for the ops team (Next.js 16), port 3002
packages/
  api/        Typed API client generated from the backend's OpenAPI spec
  session/    Access-token store and refresh logic shared by both apps
  ui/         Design tokens (Tailwind 4 theme), shared components, Kigali formatting and places
```

## Getting started

```bash
pnpm install
cp apps/client/.env.example apps/client/.env.local   # then fill in the values
cp apps/admin/.env.example apps/admin/.env.local
pnpm dev:client                                      # http://localhost:3001
pnpm dev:admin                                       # http://localhost:3002
```

Both apps need the backend running at `NEXT_PUBLIC_API_URL` (e.g. `http://localhost:3000`), with their origins listed in the backend's `CORS_ORIGINS`.

### Authentication

The API issues its own tokens (see the backend README):

- **Access token:** kept only in memory (`packages/session`). It's refreshed a minute before it expires, and once on page load.
- **Refresh token:** an `httpOnly` cookie set by the API. Scripts can't read it, and it's only sent to `/v1/auth/*`. Browsers only send it if the app and the API look like the **same site**, so each app reaches the API one of two ways:
  - **Proxy (deployment): set `API_ORIGIN`.** The browser calls `/v1/*` on the app's own origin and Next forwards it to the API (`next.config.ts` rewrites). The cookie belongs to the app's domain, so the app and API can live on unrelated domains, e.g. two `*.onrender.com` hosts. Uploads and `Set-Cookie` pass through unchanged.
  - **Direct (local dev): set `NEXT_PUBLIC_API_URL`.** The browser calls the API itself, which only works same-site: `localhost` ports, or sibling subdomains such as `app.example.rw` and `api.example.rw`.

  Either way, each app's public origin goes in the API's `CORS_ORIGINS`, since the API checks `Origin` on the cookie endpoints and the proxy passes it through.
- **Refreshing:** one at a time, across all tabs, using the Web Locks API. Refresh tokens rotate, so two simultaneous refreshes would look like token theft and end the session.
- **Two apps, two sessions:** the admin console passes `?app=admin` to `/v1/auth/*`, so its refresh cookie (`th_refresh_admin`) is separate from the client app's (`th_refresh`). Signing out of one doesn't sign you out of the other.

## Updating the API client

After changing the backend's endpoints, regenerate the types with the backend running:

```bash
pnpm api:generate   # reads http://localhost:3000/docs/openapi.json
```

`packages/api/src/schema.d.ts` is generated but committed, so the apps build without the backend running.

## Client app

The 14 screens of the MVP design map onto these routes:

| Design                     | Route                                           |
| -------------------------- | ----------------------------------------------- |
| 1–3 Sign up                | `/signup`, `/signup/about`, `/signup/verify`    |
| 3b Notifications/location  | `/signup/permissions`                           |
| 4 Overview                 | `/`                                             |
| 5 New request              | `/requests/new`                                 |
| 6 My requests              | `/requests`                                     |
| 7 Review & pay, 8 Confirmed | `/requests/[id]` (the view depends on status)   |
| 9 Rate & feedback          | `/requests/[id]/review`                         |
| 10 Payments                | `/payments`                                     |
| 11 Profile                 | `/profile`                                      |
| 12 Report an issue         | `/help` (`?request=<id>` preselects the booking) |
| 13 Install                 | `/install`                                      |

The profile's "Personal details", "Verification" and "Notifications" links reuse the sign-up screens with `?edit=1`.

The list of services comes from the API (`GET /v1/service-types`), so ops can add or hide services without a release.

**Long-term services** (house help, or a driver chosen as long-term) change the New request form. It asks for a start date, live-in or live-out, days a week, and an optional monthly salary instead of a time and duration. The rest of the flow adapts too:

- Review & pay shows a one-off **match fee**.
- The confirmed screen shows **"Starts …"** instead of an arrival time.
- The client confirms with **"They've started"** rather than "Mark as done".

Not built yet, because the backend endpoints don't exist yet: ID upload, vouchers and the profile photo.

Implementation notes:

- **Times.** All times are shown and entered in Kigali time (UTC+2), whatever the device's timezone.
- **PWA.** The manifest and icons are generated by Next (`app/manifest.ts`, `app/icons`). `public/sw.js` only provides an offline fallback page; no personal data is cached.
- **Payments.** "Accept & pay" sends a MoMo prompt, then polls `GET /v1/payments/:id`, which also re-checks the status with MoMo, until the payment is approved or fails.

## Admin console

The ops team's console (`apps/admin`). The nine screens of the admin design map onto these routes:

| Route | Screen |
| --- | --- |
| `/` | Dashboard: queue counts, requests needing action, workers to verify, wallets |
| `/requests`, `/matching` | Request pipeline (kanban) and the to-price/to-confirm list |
| `/requests/[id]` | Price & match: suggested workers, hold one, send the price, confirm after payment, refund |
| `/workers`, `/workers/new`, `/workers/[id]/edit` | Workers list and the six-section add/edit form with a live checklist |
| `/workers/[id]` | Verify worker: ID documents, "Check against the ID", decision, activity, wallet |
| `/clients`, `/clients/[id]` | Clients and their recent requests (no design; plain tables) |
| `/payments` | Platform/escrow/wallet totals, transactions (CSV export), withdrawals and payouts, refunds |
| `/support` | Customer service tickets: status, assignee, notes, emailed replies, refunds |
| `/settings` | Fees, release window, matching priority, service types, MoMo switch, team & invitations |

- **Who sees what.** The API's `/v1/admin/me` returns the staff member's permissions. The sidebar and each action are hidden without the matching permission, and the API enforces the same rules. Accounts without a staff role are signed out at login.
- **Files.** Worker documents, ticket attachments and the CSV export need the bearer token, so they're fetched with it and shown through object URLs (`src/lib/files.ts`).
- **First admin.** Register through the client app, then run `pnpm admin:promote <email>` in the backend. Invite everyone else from Settings & team.

## Deploying

Each app is a Node web service (it can't be a static site: request pages are dynamic and the proxy needs a server). On Render, for each app:

| Setting | Value |
| --- | --- |
| Root directory | empty (the shared packages are at the repo root) |
| Build | `corepack enable && pnpm install --frozen-lockfile && pnpm --filter @trustedhands/client build` (or `@trustedhands/admin`) |
| Start | `pnpm --filter @trustedhands/client exec next start --port $PORT` (or `@trustedhands/admin`) |
| `API_ORIGIN` | the API's **private** URL if your plan has private networking (e.g. `http://trustedhands-api:10000`), otherwise its public URL |
| `NODE_VERSION` | `22` |

`API_ORIGIN` is read when the app is built, so redeploy after changing it. On the API, set `CORS_ORIGINS` to both apps' public URLs, `ADMIN_APP_URL` to the admin's, and `TRUST_PROXY_HOPS` to `1` when the apps use the private URL (`2` with the public URL, as requests then pass the API's load balancer too). MoMo callbacks go to the API's public URL directly.
